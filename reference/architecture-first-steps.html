One project, one path

MySQL → dlt → raw ClickHouse → dbt → sales mart → dashboard. dlt moves selected rows; dbt transforms them inside ClickHouse. Raw data and marts can share one warehouse. The dashboard reads the mart; it is not the mart.

The questions to ask when reviewing an architecture
ConceptDefinition / decisionFactory example
OLTP / OLAPOperational transactions and focused lookups / analytical calculations and comparisons.Check order 100 / compare a year of sales by flavor.
PipelineThe repeatable movement and processing workflow, not a storage table.Extract, load, transform, and check.
Warehouse / martBroader integrated analytical data / a focused business dataset.Sales, production, and inventory / daily sales.
Source / destinationRead from / write to, relative to a particular step.Raw ClickHouse tables are ingestion’s destination and transformation’s source.
Batch / streamingBounded groups processed in runs / a continuing event flow.Hourly sales refresh / continuously process arriving events.
ETL / ELTExtract, transform, load / extract, load, transform. Locate transformation relative to the analytical destination.Remove forbidden fields before loading / load raw rows, then model sales in SQL.

Three questions, three separate decisions

  1. What work? Operational transactions or analytical questions?
  2. Where transform? Before or after loading the analytical destination?
  3. When process? Scheduled bounded runs or a continuing event flow?

Our starting point: MySQL handles OLTP; ClickHouse supports OLAP; the analytical pipeline is batch ELT. These labels answer different questions and can coexist.

Avoid shortcuts in reasoning: OLTP can read. A mart need not have its own server. Faster polling is still polling. ELT never overrides a rule against storing prohibited data. Streaming is not a zero-latency guarantee.
