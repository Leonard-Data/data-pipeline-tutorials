OLTP records business. OLAP explains it.

OLTP means online transaction processing: short operational actions, such as saving an order, changing its status, or looking up one customer's order. OLAP means online analytical processing: analysis across data, such as comparing sales by flavor over a year. Microsoft’s explanation grounds this distinction.

Do not memorize “writes versus reads.” An OLTP lookup is a read, too. These are workload descriptions, not immutable product labels. Small reports can run in MySQL; we separate analytics here to learn the architecture and its trade-offs.

A pipeline moves data. A warehouse holds it.

A pipeline is the repeatable workflow that moves and processes data. A warehouse integrates analytical data for questions across the business. A mart is a focused analytical dataset: here, daily sales for the manager. A mart is not the dashboard itself. Pipeline stages · Warehouse versus mart.

ETL or ELT: where does transformation happen?

Extract reads the source. Load writes to the analytical destination. Transform changes structure or business meaning: filter cancelled lines, calculate net sales, or group by day. The important difference is the order around loading the destination. ETL/ELT comparison.

ETL
  1. Extract
  2. Transform
  3. Load

Prepare the data before it lands in the analytical destination.

ELT
  1. Extract
  2. Load
  3. Transform

Land source-oriented data first; transform it within the warehouse.

Our project uses ELT: dlt loads source rows into ClickHouse, then dbt builds analytical models there. Use this when warehouse SQL and keeping source-oriented data serve the requirements.

When would you change the order? If a contract forbids customer names in the analytical destination, remove or replace those names before loading it. That is an ETL-style transformation at this boundary. You can still perform further transformations afterward.

ELT does not mean “skip validation and load secrets.” Neither pattern is universally faster, safer, or better. Loading can include technical normalization without changing our overall ELT classification.

Batch or streaming: when does data move?

Batch processes a bounded group of data: for example, all rows selected for an hourly run. Streaming processes a continuing flow of events as they arrive. Shorter batch intervals are still batches; streaming is not a promise of zero delay. Beam’s bounded/unbounded distinction.

For an hourly sales report, start with batch. For a requirement to react to new events within seconds, investigate streaming and its operational cost. Timing is separate from ETL/ELT: a pipeline can be both batch and ELT, as ours will be.

Code along: same answer, different path.

Save this as first_pipeline.py and run python3 first_pipeline.py. It uses only Python’s standard library. Lists and dictionaries stand in for storage; this is not a real warehouse or a dlt/dbt implementation.

Predict first: three source lines include one cancellation. Should the sales mart count all three? Amounts are synthetic USD cents; the shipped lines total $45.00.

source_rows = [
    {"line_id": 1, "status": "shipped", "net_cents": 1800},
    {"line_id": 2, "status": "shipped", "net_cents": 2700},
    {"line_id": 3, "status": "cancelled", "net_cents": 5000},
]

def summarize(rows):
    shipped = [row for row in rows if row["status"] == "shipped"]
    return {
        "shipped_lines": len(shipped),
        "net_cents": sum(row["net_cents"] for row in shipped),
    }

# ELT: copy source-shaped rows into our pretend warehouse, then transform.
warehouse_raw = [row.copy() for row in source_rows]
mart_elt = summarize(warehouse_raw)

# ETL: transform first, then load the resulting summary.
prepared_before_load = summarize(source_rows)
mart_etl = prepared_before_load.copy()

expected = {"shipped_lines": 2, "net_cents": 4500}
assert mart_elt == expected
assert mart_etl == expected
assert len(warehouse_raw) == 3
print(mart_elt)

Expected output: {'shipped_lines': 2, 'net_cents': 4500}. The answers agree; the order and retained raw data differ.

Your variation: add a shipped line worth 900 cents. Predict the new result, update expected, and run again. The existing raw-row count assertion must change too. Why?

Answer key · open after attempting the questions
  1. OLTP transaction processing. A short operational lookup can be a read.
  2. A sales mart. A focused dataset; not a separate server requirement.
  3. The transformation source. Source/destination are relative to the step.
  4. Scheduled batch processing. Frequency alone does not define streaming.
  5. Extract load transform. The business transformation follows the load.
  6. Transform before loading. Respect the contract before the data crosses the boundary.
