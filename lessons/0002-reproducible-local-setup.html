Before moving factory orders, make sure you know which machine runs your tools—and how to recreate their Python environment.

Your win: run isolated Python, repeat its dependency installation from a lockfile without deleting anything, and prove Docker can run a disposable container.

One project. Its own Python.

A virtual environment isolates a project’s Python packages from other environments. We use uv to manage it; uv run selects the project environment without manual activation. Read Python’s explanation of isolation and uv’s project guide.

Our baseline is Python 3.12. At this lesson’s source check, it remains security-supported, and falls within dlt’s documented Python range. This is not a tested compatibility matrix for Dagster, dbt, adapters, or dashboards. Do not install the whole stack yet or replace Ubuntu’s system Python.

Use a new, empty directory. Run this block once. The first guard rejects a pre-existing UV_PROJECT_ENVIRONMENT override, which could direct installs outside the lab. If that guard fails, ask before changing your configuration. If the folder already exists, the && chain also stops: choose a fresh name consistently rather than overwriting work.

Ubuntu terminal · create the new lab

test -z "${UV_PROJECT_ENVIRONMENT:-}" &&
mkdir "$HOME/factory-setup-lab" &&
cd "$HOME/factory-setup-lab" &&
uv init --bare --vcs none --python 3.12 &&
uv python pin 3.12 &&
uv add dlt

uv can download the requested interpreter when needed. uv add dlt installs the core library and resolves its dependencies; it does not load factory data or install our database drivers. This introduces one relevant dependency so that the lockfile exercise is real. Managed Python · Managing dependencies.

uv run --locked python --version

Check: Python reports 3.12.x, dlt prints a version, and uv.lock exists. Your exact resolved versions are observations to record—not numbers copied from this page. --locked refuses a missing or outdated lock rather than silently changing it.

Prove which environment runs the code.

Save the following as check_environment.py in the lab directory. Predict what “Isolated” will show. Python documents the prefix comparison used here.

Python file · save inside the Ubuntu lab — do not paste this into PowerShell or a Bash prompt.

import sys
from pathlib import Path

assert sys.prefix != sys.base_prefix, "Use uv run --locked python check_environment.py"
assert sys.platform == "linux", "Use Python inside Ubuntu / WSL for this lesson"

print("Python:", sys.version.split()[0])
print("Isolated:", sys.prefix != sys.base_prefix)
print("Environment:", Path(sys.prefix).name)

Ubuntu terminal · run the saved file

uv run --locked python check_environment.py

Expected: Python: 3.12.x, Isolated: True, Environment: .venv. The assertions check isolation and Linux; you must also check the printed version and environment name. An active environment alone does not prove it is the intended project’s environment.

Rebuild from the lock, not from memory.

Predict: will a second installation change uv.lock? Run inside the same lab. uv sync --locked synchronizes installed packages to the lock without updating it; it can remove extra packages from that environment. Use it only in this isolated lab—not against system Python.

Ubuntu terminal · synchronize the existing lab

sha256sum uv.lock
uv sync --locked
uv run --locked python check_environment.py
sha256sum uv.lock

Check: the two hashes match and isolation still passes. This verifies the lock was unchanged; it does not yet prove a fresh environment was reconstructed.

Now try a genuinely separate environment.

First confirm .venv-replay does not already exist. The following documented environment-path override applies only to each prefixed command. It creates a second environment without deleting the first. Never point it at a system or shared directory.

Ubuntu terminal · recreate from the same lock

test ! -e .venv-replay &&
UV_PROJECT_ENVIRONMENT=.venv-replay uv sync --locked &&
UV_PROJECT_ENVIRONMENT=.venv-replay uv run --locked python check_environment.py

Expected: Isolated: True and Environment: .venv-replay. The original .venv remains intact. If the first guard fails, stop or choose a fresh replay name in every occurrence; do not remove existing directories. This is the same uv workflow, not a second package manager.

Independent variation: run the dlt version command from the previous section with the same UV_PROJECT_ENVIRONMENT=.venv-replay prefix. Compare it with the original environment. Explain why the dependency versions agree even though the environment directories differ.

Check your explanation after trying

Both environments install from the same uv.lock on the same platform/interpreter line. A lock records the resolved dependencies; the environment is their installation. Locking does not pin your Windows build, Docker image, interpreter patch, or external data, and does not prove every platform or future adapter combination works.

Version the recipe, not the environment.

Still inside this newly created lab, initialize a local Git repository. Append ignore rules; stage only the named files. No remote, account, commit identity, or push is required.

Ubuntu terminal · lab directory only

git init
printf '\n.venv/\n.venv-replay/\n.env\n.dlt/secrets.toml\n__pycache__/\n' >> .gitignore
git add pyproject.toml uv.lock .python-version .gitignore check_environment.py
git status --short

Check: the five named files are staged; neither virtual environment is. Do not use git add . as a substitute for checking. Keep passwords, tokens, and future connection secrets out of both Git and your exit report.

If --locked fails: stop and read the error. Compare your intended requirements with pyproject.toml and the lock. Deliberate dependency changes should be resolved and reviewed with uv; do not delete the lock or switch to --frozen merely to silence a mismatch.

A Docker client is not a running engine.

Docker Desktop manages the local engine on Windows; the Docker CLI sends it commands. Compose describes and runs multi-container applications. Desktop already includes the Compose plugin; do not install the legacy standalone docker-compose for this path.

  1. After passing the preflight, use the official Windows installer matching your architecture. Review the terms before accepting; do not purchase anything for this lesson.
  2. Start Docker Desktop from Windows. Use its WSL 2 based engine and Linux containers.
  3. Under Settings → Resources → WSL Integration, enable your Ubuntu distribution and apply the change. If the menu is missing, check Linux-container mode. Follow Docker’s WSL instructions; labels may change with Desktop versions.
  4. Reopen Ubuntu and run the checks below. Do not also install Docker Engine with apt inside Ubuntu: Docker warns that the two installations can conflict.

Ubuntu terminal · Docker Desktop running on Windows

docker --version
docker version
docker compose version
docker run --rm hello-world
Four commands, four different pieces of evidence
ObservationWhat it provesWhat it does not prove
docker --versionThe CLI is available.The engine is reachable.
docker versionSuccessful Client and Server sections show communication with an engine.A database or our factory stack is ready.
docker compose versionThe Compose plugin is available.A multi-service configuration has been tested.
hello-world succeedsA small container ran and exited. Look for “Hello from Docker!” and a successful command exit.Storage, database credentials, ports, and application images have been validated.

--rm removes the exited smoke-test container, not its cached image. The image may need a network download. Its default tag is a convenience for this disposable check, not our future application’s image-pinning policy. Docker’s cleanup reference.

When a check fails: stop, locate, then repair
  • Docker command not found in Ubuntu: confirm Desktop is installed, running, and integrated with this distribution. Reopen Ubuntu.
  • CLI version works, Server connection fails: check Desktop’s engine status, WSL integration, and Linux-container mode. Do not solve it by installing a second engine, using sudo, opening an unauthenticated TCP daemon, or weakening socket permissions.
  • Image pull fails: record the network/proxy/rate-limit error. It is not evidence that Python isolation failed. Do not disable TLS verification.
  • uv chooses the wrong place: check the current directory and .python-version. Run via uv run --locked in this lab. Ask before changing a global interpreter or an existing environment override.
  • Resources or permissions are insufficient: pause for a smaller or administrator-approved plan. No cloud signup, factory databases, volume deletion, or broad Docker cleanup is required here.
